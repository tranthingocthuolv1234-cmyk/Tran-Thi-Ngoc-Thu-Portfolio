ParkFlow B

Smart Parking Optimization

SUMMARY

ParkFlow B is an academic smart-parking case study that explores how automated access, cashless payment, and real-time parking information could improve the parking experience at UEH Campus B. My Business Analyst contribution focused on root-cause analysis, AS-IS/TO-BE process modeling, requirements, use cases, and low-fidelity wireframes.

01

OVERVIEW

Problem and context

ParkFlow B was designed for a campus parking context serving an estimated 500+ daily users. The project examined how manual gate operations, cash-based payments, and limited access to parking information could contribute to congestion and operational workload.

01

Manual Operations

Ticketing, identity checks, barrier control, and cash handling depend heavily on parking staff.

02

Information Gap

Students have limited visibility into parking availability before arriving.

03

Administrative Burden

Manual records make it more difficult to monitor transactions, parking status, and exceptions.

04

Payment Friction

Cash payment can slow exit processing and create reconciliation issues.

Design question

How might UEH Campus B redesign the parking journey to reduce manual processing while improving payment transparency, parking visibility, and security?

02

ROLE

Analyzed the existing parking workflow and mapped the AS-IS and proposed TO-BE processes to identify operational gaps.

Requirement Analysis

Translated identified pain points and stakeholder needs into business, functional, integration, and non-functional requirements.

03

ROOT CAUSE

Root-cause analysis

To structure the causes of peak-period congestion, I used a Fishbone (Ishikawa) diagram covering six categories: Management, Environment, Methods, Measurement, People, and Technology.

The analysis suggested that manual operational steps and limited real-time data visibility were central contributors to delay and uncertainty. These are analytical findings to validate, rather than empirically proven causes.

Artifact purpose

To organize potential causes of congestion and determine which issues should be addressed by the TO-BE process.

What it clarified

The solution needed to address not only gate speed, but also payment, information visibility, operating workload, and system integration.

04

STAKEHOLDERS

Stakeholder analysis and mapping

The stakeholder model considers UEH Management, the external parking operator, the IT Department, students, and security guards. Their needs should be validated during later workflow and usability testing.

Decision and approval stakeholders

UEH Management and the external parking operator have significant influence over project feasibility, operating rules, financial transparency, and reconciliation.

Technical gatekeeper

The IT Department influences security, infrastructure compatibility, data integration, and system support requirements.

Primary users and operators

Students and security guards have lower formal decision authority but strong influence over usability, daily operation, and exception handling.

Artifact purpose

To distinguish decision authority, operational impact, technical influence, and user needs.

Decision supported

To separate management-dashboard requirements from student-facing and gate-operation requirements.

05

AS-IS / TO-BE

Current state — AS-IS

The AS-IS analysis used an estimated average processing time of approximately 30 seconds per transaction as a working baseline.

  • Security guards issue or verify parking access manually.
  • Entry and exit depend on several human-operated steps.
  • Cash payment contributes to exit delays.
  • Students cannot reliably check parking availability before arrival.
  • Transaction records and parking history are not easily visible to students.

Future state — TO-BE

The TO-BE design targets reducing standard transaction time to under 15 seconds. This is a design target, not a measured production result.

  • LPR or NFC-based identity verification
  • Automated barrier control
  • Entry and exit transaction recording
  • Cashless payment
  • Parking availability updates
  • Entry and exit notifications
  • Exception handling

Artifact purpose

To identify where manual steps could be removed, automated, or supported by clearer system information.

07

USER STORIES

US-01 Automated Entry and Exit — Hybrid LPR/NFC

As a student, I want to enter and exit using LPR or an NFC card, so that I can complete the standard gate process with minimal manual interaction.

  • Given registered vehicle or NFC data is available, when the student approaches the gate, then the system attempts to match the presented identity with the registered account.
  • Given identity matching succeeds, when verification is completed, then the barrier-opening request is triggered.
  • Given the entry or exit event is recorded, when the transaction is completed, then a confirmation containing the time and vehicle identifier is available to the student.
  • Given verification fails, when the system cannot confirm identity, then the barrier remains closed and an exception path is provided.
  • Performance targets: identity matching within two seconds; standard gate flow within five seconds. These are targets, not measured outcomes.
US-02 Seamless E-Wallet Integration

As a student, I want to link a payment method, so that parking fees can be processed without manual cash handling.

  • Given the student opens payment settings, when supported providers are displayed, then the student can select an available bank or e-wallet.
  • Given the student submits account information, when provider verification is required, then the system supports a secure verification step.
  • Given account linking succeeds, when verification is completed, then the linked-payment status is displayed.
  • Given linking fails, when the provider returns an error, then the system displays a clear failure message and retry path.
  • Named providers in the wireframe are conceptual examples; active integrations are not claimed.
US-03 Entry and Exit Security Notifications

As a student, I want to receive entry and exit notifications, so that I can confirm when my vehicle is recorded by the parking system.

  • Given the barrier event is completed, when the transaction is recorded, then the system creates a notification.
  • The notification includes the available vehicle image, timestamp, parking location, and event type.
  • Given the student opens the notification, when details are available, then the related transaction record is displayed.
US-04 Lost NFC Card Control

As a student, I want to deactivate a lost NFC card, so that it cannot be used for unauthorized parking access.

  • Given the student selects card deactivation, when the action is initiated, then the system displays a clear warning.
  • Given the student confirms the action, when identity verification succeeds, then the NFC card is marked inactive.
  • Given deactivation succeeds, when processing is completed, then a confirmation state is displayed.

Artifact purpose

To convert high-level requirements into testable user behavior, system responses, and exception states.

Payment and Notification Module

This model separates student-facing payment and notification goals from the supporting fee, status, receipt, and failure behavior.

Functions

  • Complete exit payment
  • Calculate and process the parking fee
  • Update payment status
  • Generate and view the receipt
  • View entry/exit notification

Analysis

Artifact purpose: To separate standard payment behavior from payment-provider integration and exception handling.

What it clarified: The flow required success, pending, declined, timeout, and insufficient-balance states.

Related requirements: FR-04, FR-05, FR-07, IR-01.

Gate Automation Module

This model isolates the student's entry and exit goals from identity verification, barrier control, transaction recording, and capacity updates.

Actors and functions

Analysis

Artifact purpose: To distinguish the student's gate action from device verification, barrier control, transaction recording, and parking-capacity updates.

What it clarified: Automated gate access depended on coordinated device, controller, and transaction services.

Related requirements: FR-01, FR-02, FR-03, IR-01, NFR-01.

This model separates daily operating functions for the parking operator and security guard from higher-level management visibility.

Actors and functions

11

LESSONS

Through this project, I learned how to connect an operational problem with structured BA artifacts. Root-cause analysis helped frame the problem, stakeholder mapping clarified different priorities, and the AS-IS/TO-BE comparison provided a basis for defining requirements.

The most important lesson was that a proposed feature should be traceable to a user pain point, stakeholder need, process gap, or operational goal.

Additional lessons

  • Performance targets should be separated from measured outcomes.
  • Integration requirements need explicit failure and reconciliation rules.
  • A happy-path process is not sufficient for gate, payment, and device workflows.
  • Low-fidelity wireframes clarify requirements but do not replace usability validation.

Limitations

  • The prototype is low-fidelity and not fully implemented.
  • The 500+ user figure is an estimated project context unless supported by official data.
  • The 30-second baseline and under-15-second target are assumptions, not verified production measurements.
  • Real-time availability depends on reliable sensor or operating data.
  • Payment integration is conceptual.
  • LPR/NFC workflows require additional exception handling.
  • User testing was limited.

Next steps

  1. Develop a higher-fidelity clickable prototype.
  2. Validate current-state assumptions with students, guards, operators, and management.
  3. Define payment timeout, failure, refund, and reconciliation rules.
  4. Add plate mismatch, unreadable NFC, device, payment, and barrier exception flows.
  5. Define data ownership, privacy, retention, and access-control rules.
  6. Validate capacity data and update frequency.
  7. Conduct usability testing for student and staff workflows.
  8. Define a measurable validation plan for transaction-time targets.
